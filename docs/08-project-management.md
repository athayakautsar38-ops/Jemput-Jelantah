**Project:** Jemput Jelantah

**Initial Pilot Area:** Jember, East Java
**Project Duration:** 7 Weeks
**Project Owner:** Product Manager
**Project Stage:** MVP Development & Validation

---

# 2. Project Objective

The project aims to design and build an MVP that can validate whether fragmented UCO supply from households and culinary micro-UMKM can be aggregated into sufficiently dense pickup routes.

The project follows the sequence:

> **DISCOVER → DEFINE → DESIGN → BUILD → TEST → PILOT → DECIDE**

The immediate objective is **not to prove business scale or profitability**, but to generate sufficient product and operational evidence for the next product decision.

# 12. Schedule Logic

The schedule follows product dependencies.

### Discovery before Strategy

User research provides evidence for:

* target segments
* problem definition
* opportunity
* hypotheses

### Strategy before Development

Product strategy defines:

* positioning
* product goals
* requirements
* MVP scope

### UX before Final Implementation

User flow and interaction states should be defined before implementation of the corresponding features.

### MVP before Operational Experiment

The operational experiment depends on the core workflow being functional.

### Pilot before Scale Decision

A scale decision requires actual operational evidence.

---

# 13. Critical Path

The critical path is:

> **Research → Problem Definition → Product Strategy → Requirements → UX → MVP → Testing → Pilot → Validation → Decision**

Delays in these activities may affect the final validation timeline.

The most critical dependency is:

> **MVP readiness → Pilot readiness → Actual validation data**

Without a functional MVP and operational readiness, route-density conclusions should not be treated as validated.

# 18. Risk Management Framework

Risks are prioritized using:

> **Impact × Likelihood**

Each risk receives:

* risk level
* mitigation
* trigger
* owner
* contingency

---

# 19. Risk Register

| Risk                                               | Impact | Likelihood | Mitigation                                        | Trigger                          |
| -------------------------------------------------- | ------ | ---------- | ------------------------------------------------- | -------------------------------- |
| Route volume remains below 50L                     | High   | High       | Densify nearby suppliers around anchors           | Route repeatedly below threshold |
| Supplier contribution is inconsistent              | High   | High       | Track historical contribution and repeat behavior | Large volume variance            |
| Pickup requests are geographically scattered       | High   | High       | Restrict initial pilot area                       | Low supplier concentration       |
| Estimated volume differs significantly from actual | High   | Medium     | Track estimated vs actual                         | Large variance                   |
| UCO price changes                                  | High   | Medium     | Use effective-dated pricing reference             | Pricing changes                  |
| Duplicate weighing/payout                          | High   | Low        | Unique request ID + validation                    | Duplicate transaction            |
| Supplier distrusts weighing                        | Medium | Medium     | Show actual volume + payout/L + total payout      | Payout complaint                 |
| Household participation is insufficient            | Medium | Medium     | Use micro-UMKM as potential route anchors         | Low household contribution       |
| Data quality issues                                | Medium | Medium     | Validation rules and QA checks                    | Missing/invalid records          |
| Geographic expansion happens too early             | High   | Medium     | Define expansion gate                             | Insufficient pilot evidence      |

---

# 20. Risk Response Strategy

## Route Volume Risk

If routes repeatedly fail to approach the internal threshold:

1. increase local supplier density
2. identify stronger route anchors
3. adjust collection windows
4. evaluate collection radius
5. reassess threshold assumption

---

## Supplier Consistency Risk

If supplier contribution is inconsistent:

1. track actual contribution history
2. identify recurring suppliers
3. distinguish anchor and densifier behavior
4. adjust route planning assumptions

---

## Pricing Risk

If UCO market pricing changes:

1. record pricing effective date
2. record pricing source
3. update payout configuration
4. recalculate commercial assumptions

---

# 21. Issue Management

Issues discovered during development are classified into:

### Critical

Blocks core workflow or causes incorrect transaction data.

Examples:

* payout calculation error
* duplicate payout
* data loss
* route threshold calculation failure

### Major

Feature works incorrectly but a workaround exists.

### Minor

Does not block core workflow.

Examples:

* UI inconsistency
* non-critical validation message
* visual issue

### Resolution Priority

> **Critical → Major → Minor**

Critical issues must be resolved before operational pilot readiness.

---

# 22. Change Control

Product changes are evaluated based on:

1. User impact
2. Business impact
3. Validation impact
4. Development effort
5. Timeline impact

### Change Rule

A change should be included in the MVP only when it:

* supports the core hypothesis
* fixes a critical usability or data problem
* is required for operational validation

Features that do not contribute directly to MVP validation should be deferred.

---

# 23. Example Change Decision

### Request

Add advanced real-time route optimization.

### Assessment

**User impact:** Medium
**Business impact:** Potentially high
**Validation relevance:** Low for initial hypothesis
**Development effort:** High
**Timeline impact:** High

### Decision

Defer from MVP.

Reason:

> The initial MVP needs to validate whether aggregation itself can create sufficiently dense routes before optimizing route sequencing.

This keeps scope aligned with the core product hypothesis.

# 34. Final Project Principle

> **Build only what is needed to test the core hypothesis, measure what matters, and make the next product decision from evidence.**

For Jemput Jelantah, this means:

> **Validate Route Density → Validate Economics → Validate Repeatability → Consider Geographic Expansion**

rather than expanding scope before the core aggregation model is understood.
