# Product Requirements Document

## 1. Product Documentation

### Product

Jemput Jelantah

### Product Type

Scheduled used cooking oil (UCO) collection and aggregation platform.

### Pilot Market

Jember, East Java.

### Primary Supplier Segments

* Culinary micro-UMKM
* Households located around target collection areas

### Product Objective

Validate whether fragmented UCO supply can be aggregated into sufficiently dense pickup routes while maintaining a convenient and transparent supplier experience.

---

# 2. Background

## 2.1 Background

Used cooking oil is generated by multiple supplier types, including households and culinary micro-UMKM.

The amount generated by each supplier can vary significantly. Small household contributions can also be geographically dispersed.

This creates a potential operational challenge: collecting suppliers individually may result in inefficient routes when the combined volume is insufficient.

Jemput Jelantah is designed to test an aggregation model where suppliers within the same area are grouped before a pickup route is dispatched.

---

# 3. Problem Definition

## 3.1 Problem Statement

> How might we aggregate fragmented UCO supply from households and culinary micro-UMKM into sufficiently dense pickup routes while maintaining a convenient and transparent supplier experience?

## 3.2 Root Cause

The working root-cause chain is:

**Fragmented Supply**

↓

**Uneven Supplier Contribution**

↓

**Insufficient Route Density**

↓

**Risk of Low Route Utilization**

The MVP focuses on testing whether aggregation can address the route-density problem before geographic expansion.

# 5. Product Hypotheses

## 5.1 Core Hypothesis

If nearby household suppliers are aggregated around culinary micro-UMKM anchors, total route volume can move toward the internal 50L pilot operating threshold without immediately expanding geographic coverage.

## 5.2 Supporting Hypothesis — Scheduled Pickup

If suppliers can select a defined area and pickup window, collection can become more predictable for suppliers and operations.

## 5.3 Supporting Hypothesis — Transaction Transparency

If suppliers can see the pricing reference, actual weighed volume, and payout calculation, the transaction can become easier to understand and verify.

## 5.4 Supporting Hypothesis — Household Densification

If households are recruited around existing micro-UMKM anchors, incremental supply can be added within an existing route instead of creating isolated pickup destinations.

# 6. Product Strategy

The MVP follows this operating model:

**Micro-UMKM**

→ Potential Route Anchor

↓

**Nearby Households**

→ Route Densifiers

↓

**Area-Based Aggregation**

↓

**Scheduled Pickup Route**

↓

**Weighing**

↓

**Verified Payout**

The product is not positioned as a unique pickup service. The primary differentiation hypothesis is the localized anchor-and-densify aggregation model combined with route-level visibility and transaction transparency.

---

# 7. 50L Internal Pilot Operating Threshold

The MVP uses **50L as an internal pilot operating threshold**.

The threshold is intended to test whether a route reaches a meaningful aggregated volume before further geographic expansion.

It is not presented as:

* an industry benchmark,
* a proven break-even point,
* a universal minimum pickup volume,
* or a proven optimal route size.

The threshold should be reassessed using actual route and cost data.

# 10. User Stories

## US-001 — Create Pickup Request

### User Story

As a supplier, I want to submit my UCO pickup request so that my contribution can be included in an upcoming collection route.

### Acceptance Criteria

* Supplier type can be selected.
* Estimated volume can be entered.
* Area can be selected.
* Pickup schedule can be selected.
* Request receives a unique request ID.
* Initial request status is recorded.

---

## US-002 — Schedule Area Pickup

### User Story

As a supplier, I want to select an available area and pickup window so that I know when collection is planned.

### Acceptance Criteria

* Available areas are displayed.
* Available pickup windows are displayed.
* Selected area and schedule are stored.
* Request is associated with the selected route grouping.

---

## US-003 — Aggregate Suppliers

### User Story

As an operations user, I want supplier requests to be grouped by area so that I can evaluate the expected volume of each route.

### Acceptance Criteria

* Requests can be grouped by area.
* Estimated volume is aggregated.
* Route progress toward the 50L internal threshold is visible.
* Route status can change based on defined conditions.

---

## US-004 — View Collection Progress

### User Story

As a supplier, I want to see the collection progress so that I understand whether my area has reached the pickup threshold.

### Acceptance Criteria

* Collected or estimated route volume is displayed.
* Target threshold is displayed.
* Remaining volume can be calculated.
* Route status is visible.

---

## US-005 — Track Pickup Status

### User Story

As a supplier, I want to know the current pickup status so that I understand whether my request is still pending or has been completed.

### Acceptance Criteria

The system supports defined request states such as:

**Pending → Scheduled → In Progress → Completed**

---

## US-006 — Record Weighing

### User Story

As an operations user, I want to record the actual collected volume so that supplier payout is based on the verified volume.

### Acceptance Criteria

* Actual volume can be entered.
* Actual volume is associated with the correct request.
* Duplicate weighing for the same request is prevented.
* Weighing result is stored.

---

## US-007 — Calculate Supplier Payout

### User Story

As a supplier, I want to know how my payout was calculated so that the transaction is transparent.

### Acceptance Criteria

The system displays:

* Actual volume
* Supplier payout per liter
* Total payout
* Pricing reference
* Effective date

Formula:

**Total Payout = Actual Volume × Supplier Payout per Liter**

# 11. Route States

The MVP uses the following route states:

### Open

Route is collecting supplier requests.

### Ready

Route reaches or exceeds the internal 50L threshold.

### In Progress

Pickup operation has started.

### Completed

Pickup operation has been completed and actual collection can be recorded.

# 16. Product Requirements

## PR-001 — Supplier Identification

The system must allow suppliers to be identified using a phone number.

The system should avoid creating unnecessary duplicate supplier records.

## PR-002 — Supplier Type

The system must distinguish:

* Culinary micro-UMKM
* Household

## PR-003 — Estimated Volume

The system must accept estimated UCO volume before pickup.

## PR-004 — Area

The system must associate each pickup request with a defined collection area.

## PR-005 — Pickup Schedule

The system must associate a request with an available pickup window.

## PR-006 — Route Aggregation

The system must calculate aggregated estimated volume by route.

## PR-007 — Threshold

The system must identify when route volume reaches the internal 50L threshold.

## PR-008 — Progress

The system must display collection progress against the route threshold.

## PR-009 — Actual Weighing

The system must store actual collected volume after weighing.

## PR-010 — Duplicate Prevention

The system must prevent duplicate weighing records for the same pickup request.

## PR-011 — Pricing Reference

The system must retrieve the active supplier payout reference.

The pricing record should include:

* Effective date
* Supplier payout per liter
* Reference/source
* Active status

## PR-012 — Payout Calculation

The system must calculate:

**Actual Volume × Active Supplier Payout per Liter**

## PR-013 — Transaction Traceability

The request, route, weighing, and payout records must remain traceable through unique identifiers.

# 17. Data Model

The MVP uses Google Sheets as the data store.

### SUPPLIERS

Stores supplier identity and supplier type.

### PICKUP_REQUESTS

Stores pickup requests, estimated volume, area, schedule, and request status.

### ROUTES

Stores route grouping, estimated volume, threshold, and route status.

### WEIGHING_PAYOUT

Stores actual volume and supplier payout transaction.

### PRICING

Stores active pricing references and effective dates.

### DASHBOARD

Stores operational metrics.

### VALIDATION

Stores validation or test-related records where applicable.

---

# 18. Pricing Logic

The MVP separates:

**Reference Price**

from

**Supplier Payout**

This allows the system to show the commercial reference while maintaining a specific supplier payout value.

Example structure:

```text
Reference Price/L
↓
Supplier Payout/L
↓
Actual Volume
↓
Total Supplier Payout
```

The values are configurable and should not be interpreted as a verified live market price unless supported by a verified external source.

# 19. Success Metrics

## 19.1 Primary Product Metric

### Liters per Route

Formula:

**Total Actual Collected Liters ÷ Completed Routes**

Initial target:

**≥50L on tested route**

---

## 19.2 Product Metrics

### Route Threshold Achievement

Percentage of tested routes reaching the internal threshold.

### Pickup Completion Rate

Formula:

**Completed Pickup Requests ÷ Scheduled Pickup Requests × 100%**

Target:

**≥80%**

### Repeat Contribution Rate

Percentage of suppliers who contribute again after an initial completed collection.

A baseline should be established during the pilot before setting a long-term target.

# 21. Business Metrics

The MVP should establish a baseline for:

### Route Efficiency

Relationship between actual collected volume and route operating effort.

### Recurring Supply

Frequency and consistency of supplier contributions.

### Contribution Margin per Route

Formula:

**UCO Value / Route − Supplier Payout − Route Variable Cost**

### Geographic Scalability

Ability to reproduce acceptable route performance in additional areas.

# 22. Trade-off Metrics

The product should monitor:

* Estimated vs actual volume gap
* Pickup failure rate
* Route operating cost
* Supplier payout cost
* Supplier acquisition effort
* Time required per completed route

The purpose is to ensure that improving collection volume does not create disproportionate operational cost or supplier friction.

# 23. Experiment Design

## Experiment Objective

Test whether supplier aggregation can increase route volume toward the internal 50L operating threshold.

## Core Experiment

Compare route volume before and after targeted supplier densification within a selected area.

## Intervention

Recruit or add nearby household suppliers around an existing potential micro-UMKM anchor.

## Measurement

Track:

* Number of suppliers
* Estimated volume
* Actual collected volume
* Route volume
* Route completion
* Estimated vs actual gap

## Interpretation

The experiment should be treated as directional evidence unless a controlled experimental design is used.

A pre/post increase should not automatically be interpreted as causal proof.

# 26. Risks

## Risk 1 — Route Volume Below Threshold

Impact: High

Mitigation:

Increase supplier density around existing anchors before expanding geography.

## Risk 2 — Inconsistent Supplier Volume

Impact: High

Mitigation:

Track estimated versus actual volume and recurring contribution.

## Risk 3 — Price Volatility

Impact: High

Mitigation:

Use configurable pricing references with effective dates.

## Risk 4 — Duplicate Transactions

Impact: High

Mitigation:

Unique request IDs and duplicate weighing validation.

## Risk 5 — Low Household Participation

Impact: Medium

Mitigation:

Recruit households around existing micro-UMKM anchors.

## Risk 6 — Premature Geographic Expansion

Impact: High

Mitigation:

Use route-density and route-economics validation as an expansion gate.

# 33. Conclusion

Jemput Jelantah's MVP is designed to validate a localized UCO aggregation model.

The product combines scheduled collection, area-based aggregation, collection progress, weighing, and transparent payout into one operational workflow.

The central hypothesis is that culinary micro-UMKM can act as potential route anchors while nearby households contribute incremental volume as route densifiers.

The MVP therefore prioritizes operational validation over feature breadth.

The primary question is whether fragmented UCO supply can be consistently consolidated into sufficiently dense routes while maintaining a convenient and transparent supplier experience.

The outcome of the pilot should determine whether the product should be iterated, expanded, or reconsidered.
